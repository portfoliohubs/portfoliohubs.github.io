Google AI Studio Guide: Repair Admin and User Dashboards
This guide is designed to be pasted into Google AI Studio after opening the repository:

https://github.com/portfoliohubs/portfoliohubs.github.io

The objective is to repair the dashboards without creating another partial migration or hiding errors.

The recommended final architecture is:

Firebase Authentication
        ↓
Cloudflare Worker API
        ↓
Cloudflare D1 database
        ↓
User dashboard / Admin dashboard / Public websites
ImageKit       → media storage
GitHub Actions → static page generation and deployment
GitHub Pages   → frontend and generated static pages
Firestore      → compatibility/migration only, not active dashboard storage
The current project mixes Cloudflare/D1, Firestore, GitHub Pages, and an Express server. The attached Firestore rules authorize the current admin operations, but they do not solve the data split or deployment mismatch.

3. Second prompt: enforce the architecture
After reviewing the audit, paste this:

Now prepare an implementation plan, but do not edit files yet.
Use this architecture unless you identify a documented blocker:
1. Firebase Authentication is the identity provider only.
2. Cloudflare Worker and D1 are the single source of truth for:
   - users
   - portfolios
   - clinical cases
   - published portfolios
   - slugs
   - settings
   - promo codes
   - blog publication state
3. ImageKit is the media provider, accessed only through the Worker.
4. GitHub Actions is responsible for static generation and deployment.
5. GitHub Pages serves the frontend and generated static files.
6. Firestore is legacy compatibility data only and must not be written by active dashboards.
7. The browser must never hold a GitHub PAT or any private service credential.
Create a file-by-file implementation plan.
The plan must include:
- API endpoint changes
- Worker changes
- frontend changes
- Firestore migration/compatibility strategy
- security-rule strategy
- GitHub Actions changes
- data migration strategy
- rollback strategy
- tests to add or update
- manual verification steps
Do not propose a partial migration where one feature writes Firestore and another reads D1.
Do not remove legacy Firestore data until a migration and rollback plan exists.
Do not deploy anything yet.
The plan must explicitly resolve these decisions
Database decision
All active dashboard writes must go through cloudflareApi.

The following frontend files should not directly import or use Firestore for active application data:

src/pages/AdminDashboard.tsx
src/pages/Dashboard.tsx
src/pages/PortfolioWizard.tsx
src/pages/PublicWebsite.tsx
src/pages/PublicBlog.tsx
Firebase imports may remain for Authentication. Direct Firestore imports should either be removed or isolated to a clearly documented migration utility.

Publishing decision
The frontend must not call an Express route that is unavailable on GitHub Pages.

The current /api/admin/generate-doctor-html route in server.ts is not automatically available from a GitHub Pages deployment. 
 

Use this flow instead:

Admin approves doctor
        ↓
Worker validates admin token
        ↓
Worker updates D1 atomically
        ↓
Worker dispatches GitHub workflow securely
        ↓
GitHub workflow reads published data from Worker
        ↓
Static files are generated
        ↓
GitHub Pages is deployed

7. Sixth prompt: handle Firestore rules correctly
Use the attached rules as the starting point, but do not assume they are deployed.

Review the supplied Firestore rules against the active code.
Important requirements:
1. Confirm whether the rules in the repository, Firebase Console, and test emulator are identical.
2. If Firestore is no longer used by active dashboards:
   - keep only necessary compatibility/public-read rules
   - remove unnecessary client write access
   - preserve data for migration
   - do not delete collections automatically
3. If Firestore remains active:
   - users may update only allowed profile fields
   - users must not update status, active, caseLimit, approved, isApproved, paymentConfirmed, publishedAt, or publication records
   - only verified admins or trusted backend operations may update workflow fields
   - settings containing admin metadata must not be publicly readable
   - blog write access must remain admin-only
   - published content may be public-read
   - user cases must validate ownership and document shape
4. Add rules tests for:
   - normal user own profile
   - normal user other profile
   - normal user protected status fields
   - verified admin
   - unverified admin email
   - lookalike admin email
   - anonymous public published read
   - anonymous private read
   - blog read/write
   - settings read/write
   - slug create/update/delete
   - published portfolio read/write
The supplied rules currently use broad owner writes for /users/{uid}, /portfolios/{uid}, and /users/{uid}/cases/{caseId}. That is acceptable only if those collections are strictly legacy or if field-level protection is added.
